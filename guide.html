Claude Certified Developer – Foundations
Messages API basics

Messages API: the basics

What the API is

  • One endpoint for chat and agents: POST /v1/messages. Required fields: model, max_tokens, messages
  • The API is stateless: Claude remembers nothing between calls. Your code sends the full conversation every time and decides what history to keep
  • system is a top-level parameter, not a message. Messages only have the roles user and assistant
  • The response has content (a list of blocks: text, tool_use, thinking...), stop_reason and usage (input and output tokens, cache fields)
  • max_tokens caps the output only. It is a ceiling, not a target, and a response cut by it is incomplete
  • SDKs (Python, TypeScript and others) add typed objects, retries with backoff for 429 and 5xx, streaming helpers and timeouts. Raw REST gives you full control but you write all of it yourself

Tokens and context

  • A token is a piece of a word, roughly 3-4 characters of English. Input and output are billed per million tokens, output costs more than input
  • The context window is a fixed budget that holds the system prompt, tools, history, your new input and the output. All current models have a 1M-token window and up to 128K output tokens
  • Counting tokens before sending: use the token counting endpoint, do not guess from characters
  • Sampling is probabilistic. temperature lowers or raises randomness, but even at low values answers can vary, so never rely on exact repeatability. Some newer models restrict or ignore sampling parameters, so check the model page

Roles and prefill

  • Consecutive messages with the same role are merged. The first message must be from the user
  • Putting text into the last assistant message used to steer the start of a reply (prefill). Newer models may reject it. Prefer structured outputs or clear instructions
Stop reasons and errors

Stop reasons and error handling

stop_reason: what to do for each value

  • end_turn: Claude finished. Use the answer
  • max_tokens: hit your limit. The answer is cut. Raise the limit or ask Claude to continue. If the last block is a half-written tool_use, retry with a higher limit
  • stop_sequence: one of your stop_sequences appeared. Read response.stop_sequence to see which
  • tool_use: run each requested client tool and send back tool_result blocks in the next user message
  • pause_turn: a server-side tool loop hit its iteration limit (default 10). Append the assistant response unchanged and call again
  • refusal: Claude declined. It is an HTTP 200 and is billed. Rephrase or fall back to another model, do not retry blindly
  • model_context_window_exceeded: the window filled before max_tokens. Treat the output as truncated

HTTP errors

  • 400 invalid request (bad schema, bad parameter): fix the request, retrying will not help
  • 401 bad API key, 403 no permission, 404 unknown resource or model
  • 413 request too large, 429 rate limit (or per-key spending limit), 500 server error, 529 API overloaded
  • Retry 429, 500 and 529 with exponential backoff and jitter, honour the retry-after header, use idempotent logic. Never retry 400 or 401 in a loop
  • Rate limits are measured in requests, input tokens and output tokens per minute and grow with usage tiers. Cached input tokens often do not count against input limits, so caching also raises effective throughput
  • Every response carries a request-id. Log it, support needs it
Streaming and limits

Streaming, timeouts and long outputs

Streaming

  • Set stream: true to receive server-sent events as tokens are generated. Time to first token drops, the user sees progress
  • Event order: message_start, then per block content_block_start, many content_block_delta, content_block_stop, then message_delta (carries the stop_reason and final usage) and message_stop
  • Tool input arrives as input_json_delta fragments. They are partial JSON: accumulate them and parse only after content_block_stop
  • Streaming is strongly recommended for long outputs: non-streaming requests that run very long risk network timeouts. The SDKs require streaming (or a long-request helper) when max_tokens is large
  • Errors can arrive mid-stream after a 200 status, so handle an error event

When to stream

  • Interactive UI: yes. Batch or background jobs, extraction into a database: no need
  • Streaming does not change price or quality, only delivery

Long outputs and truncation

  • Plan for max_tokens: if you need more than one response can hold, split the task into parts or ask Claude to continue from where it stopped
  • Output limits depend on the model and API (Batch API can allow more with a beta header)
Model tiers and platforms

Model tiers, platforms and choosing a model

Current lineup (Claude API IDs)

  • Fable 5.2 claude-fable-5-2: demanding reasoning and long-horizon agentic work. $8 in / $40 out per MTok
  • Opus 5.5 claude-opus-5-5: long-running agentic coding and knowledge work, the default starting point. $4 / $20
  • Sonnet 5.5 claude-sonnet-5-5: best balance of speed and intelligence. $2 / $10
  • Haiku 5.5 claude-haiku-5-5: fastest and cheapest, for classification, extraction, routing and other high-volume or latency-sensitive work. From $0.10 / $0.50
  • All four: text and image input, text output, tool use, 1M context, up to 128K output

How to choose

  • Start with the smallest model that passes your evals, move up only when measured quality is not enough
  • Typical split in one system: Haiku for routing, screening and simple extraction, Sonnet for the main workload, Opus or Fable for hard planning and difficult sub-tasks
  • Latency: smaller tiers are faster. Cost: scales with tokens, so a cheaper model that needs retries can cost more
  • Pin exact model IDs in production. Every ID is a pinned snapshot, and old models are retired on announced dates (see deprecations)

Where Claude runs

  • Claude API (Anthropic directly), Amazon Bedrock, Google Cloud, Microsoft Foundry, Claude Platform on AWS
  • Model IDs differ per platform (Bedrock IDs look like anthropic.claude-opus-5-5). Feature availability and some beta features differ per platform too
  • Choose the platform by data residency, existing cloud contracts, IAM and billing, then check that the features you need exist there
Thinking and effort

Thinking and the effort parameter

Thinking

  • Thinking lets Claude reason before answering. Reasoning tokens are billed as output tokens
  • On current models thinking is adaptive: Claude decides how much to think, steered by effort
  • The older manual mode (thinking: {type: "enabled", budget_tokens: N}, called extended thinking) belongs to earlier models. It is deprecated on some and not accepted on the newest ones. In that mode budget_tokens must be lower than max_tokens and at least 1,024
  • Thinking blocks must be passed back unchanged in multi-turn tool use so Claude keeps its reasoning. Do not edit them
  • Thinking is not free: more latency and more output tokens. Use it for hard reasoning, math, planning, difficult coding, not for classification or simple lookups

Effort: output_config.effort

  • Levels: low, medium, high, xhigh, max (not every level on every model)
  • Default is high on most models. Opus 5.5 and Haiku 5.5 default to medium
  • Effort controls overall token spending: thinking, tool calls and answer length. Lower effort = faster and cheaper, fewer tool calls and shorter text. Higher effort = more thorough
  • xhigh is for long-horizon agentic and coding work. max is for the deepest reasoning with no token constraint
  • Choosing: measure on your evals. Raise effort before you move to a bigger model, lower it for simple high-volume tasks

Rule of thumb

  • Quality too low? 1) better prompt and context, 2) higher effort or thinking, 3) bigger model
  • Too slow or expensive? 1) smaller model for easy steps, 2) lower effort, 3) caching and batch
Prompt caching

Prompt caching

What it does

  • Lets the API reuse a processed prefix of your prompt. Cuts cost and latency for repeated long context: system prompts, tool definitions, documents, long conversations
  • Prefix order is tools, then system, then messages. A change at one level invalidates that level and everything after it
  • Matching is exact, byte for byte. Keep tool JSON key order stable, never put timestamps or request IDs before the cached part

How to enable

  • Automatic: one top-level cache_control: {"type": "ephemeral"}. The breakpoint moves forward as the conversation grows
  • Explicit: put cache_control on a content block (up to 4 breakpoints per request). The breakpoint goes on the last block that is identical across requests
  • Cache reads look back up to 20 blocks from a breakpoint

Lifetime and price (multiples of the base input price)

  • 5-minute cache (default): write 1.25x. Every hit refreshes the 5 minutes for free
  • 1-hour cache {"type": "ephemeral", "ttl": "1h"}: write 2x. For prompts reused less often than every 5 minutes. Longer TTL entries must come before shorter ones
  • Read (hit): 0.1x of base by default. 0.05x on Opus 5.5 and Sonnet 5.5, 0.025x on Fable 5.x
  • Output price is unchanged. Breakpoints themselves are free

Minimum length and checks

  • Current models cache from 512 tokens, older ones need 1,024 to 4,096. Shorter prompts are processed without caching and without an error
  • Check usage: cache_creation_input_tokens and cache_read_input_tokens. If both are 0, nothing was cached. Total input = cache_read + cache_creation + input_tokens (the last counts only tokens after the final breakpoint)
  • Concurrent requests only share a cache once the first response has started. Caches are isolated per organization (and per workspace on some platforms)

What breaks it

  • Editing tool definitions, toggling web search or citations, changing tool_choice, adding or removing images, changing thinking settings (model dependent)
Batch API and cost

Batch API, cost and latency levers

Message Batches API

  • Asynchronous processing of many Messages requests at 50% off
  • Limits: up to 100,000 requests or 256 MB per batch. Most batches finish within 1 hour, but a batch expires after 24 hours
  • Each request has a unique custom_id (1-64 chars). Results can come back in any order, so always match them by custom_id
  • Result types per request: succeeded, errored, canceled, expired. One failed request does not fail the batch
  • Results stay downloadable for 29 days after creation. Batches are scoped to a workspace
  • Use for: evals, bulk classification, summarization, embeddings-like back-office jobs. Do not use for anything a user is waiting for
  • Works with prompt caching, structured outputs and tool use. The 50% and cache savings can stack

Cost levers (in order of effort)

  • Right-size the model (Haiku for easy steps), lower effort, shorter prompts, limit max_tokens
  • Prompt caching for repeated prefixes
  • Batch for non-urgent work
  • Fewer tool round-trips: parallel tool calls, better tool design
  • Trim context: summaries, retrieval of only relevant chunks instead of whole documents

Latency levers

  • Smaller model, lower effort, streaming (perceived latency), caching (faster time to first token), shorter outputs, parallel calls

Estimating cost

  • cost = input tokens x input price + output tokens x output price (thinking counts as output). Cache reads are cheap, cache writes cost more than a normal input token
  • Worked example: 20,000 cached prefix tokens on Sonnet 5.5 ($2/MTok), 50 calls in 5 minutes: one write 20,000 x $2.50/M = $0.05, then 49 reads at $0.10/M x 20,000 = $0.098 for all reads, about $0.15 in total, versus $2.00 uncached
Structured outputs

Structured outputs and strict tools

Two features

  • JSON outputs: output_config.format with type: "json_schema". Claude's text answer must match your schema (constrained decoding), so parsing never fails
  • Strict tool use: strict: true on a tool. Tool names and inputs always match the tool schema
  • Use them together: JSON outputs control what Claude says, strict tools control how it calls your functions

Rules and limits

  • Objects need additionalProperties: false. Supported: types, enum, const, anyOf, $ref/$defs, required
  • Not supported: recursive schemas, numeric constraints (minimum, maximum), string length constraints, external $ref
  • Complexity limits per request: 20 strict tools, 24 optional parameters total, 16 parameters with union types
  • The first request with a new schema is slower (grammar compilation, cached for 24 hours)
  • Casing of enum values may differ, so compare case-insensitively

Still handle

  • stop_reason: "refusal" (output may not match the schema) and "max_tokens" (output may be truncated and invalid)
  • Schema-valid does not mean correct: validate business rules yourself and evaluate accuracy

When to use what

  • Extraction, classification, reports into an API: JSON outputs
  • Reliable function calling: strict tools
  • Older way: ask for JSON in the prompt plus XML or a prefill. It works but gives no guarantee
Prompt engineering

Prompt engineering that works in production

Principles

  • Be clear and direct: say the task, the audience, the format, the constraints. Treat Claude like a smart new colleague with no context
  • Give the reason behind a rule ("do not use ellipses because a text-to-speech engine reads this") and Claude generalizes better
  • Put long documents first and the question or instruction last. This improves quality on long inputs
  • Use XML tags (<document>, <instructions>, <example>) to separate instructions, data and examples. Use consistent tag names
  • Few-shot examples: 3 to 5 diverse, relevant examples wrapped in tags. They steer format and tone strongly, so make them match what you want exactly
  • Tell Claude what to do, not only what not to do
  • Give Claude a role in the system prompt (a specific one beats "helpful assistant")

System prompt vs user message

  • System prompt: role, rules, tone, output format, policies that hold for the whole conversation
  • User message: the task and the data of this turn
  • Untrusted content belongs in tool results or clearly tagged data, never mixed into system instructions

Reasoning and format

  • For hard problems allow thinking (adaptive thinking or step by step in tags), then ask for a short final answer
  • To control output format use structured outputs, or tell Claude the format and show an example

Debugging a weak prompt

  • Look at failures, not averages. Is the instruction missing, ambiguous or contradicted? Add an example of the failing case. Check that the needed information is actually in the context
  • Change one thing at a time and re-run your eval set
  • Prompt chaining: split one complex prompt into steps (extract, then analyse, then write). Each step is easier to test
Context management

Context management and memory

The context window is a budget

  • Everything counts: system prompt, tool definitions, all history, tool results, thinking, the new answer. Quality can drop when the context is stuffed with irrelevant text
  • More context is not always better. Include what the task needs, retrieve the rest

Techniques

  • Retrieval (RAG): search a knowledge base, put only the top chunks in the prompt, ask Claude to quote or cite them. Good for large or changing knowledge
  • Summarization / compaction: replace old turns with a summary when the conversation gets long
  • Context editing: remove stale tool results and old thinking blocks automatically
  • Memory tool: a client-side tool where Claude reads and writes files you store (notes, preferences, progress) so state survives across sessions and context resets
  • Sub-agents: give a task to a fresh context, get back a short result, keep the main context clean
  • Caching: keep stable content at the front of the prompt

Practical rules

  • Order: static content (tools, system, reference docs) first, dynamic content last. Good for both quality and caching
  • Tool results can be huge: truncate, paginate or summarize them before returning to Claude
  • Long documents: place them at the top, ask the question at the end, optionally ask Claude to extract relevant quotes first
  • Conversation state is your job: store it in your own database, keyed by user or session
  • Multi-turn tool use: keep the assistant's tool_use and your tool_result blocks in history, otherwise the next request is invalid
Tool use

Tool use: definitions and the loop

Defining a tool

  • Fields: name, description, input_schema (JSON Schema). Optional strict: true
  • The description is the most important part: what the tool does, when to use it, when not to, what parameters mean and what it returns. Several sentences are normal
  • Keep schemas simple: clear names, enums for fixed choices, required fields only where truly required

The loop (client tools run in your code)

  • 1. Send tools and the user message. 2. Claude replies with stop_reason: "tool_use" and one or more tool_use blocks (id, name, input). 3. Your code runs them. 4. Send a user message that contains a tool_result for every tool_use_id. 5. Repeat until end_turn
  • Keep the same tools array on follow-up requests. Put tool_result blocks first in the user message, any text after them
  • Report failures with is_error: true and a helpful message. Claude can then retry or explain. Do not crash the loop and do not hide errors
  • Set a maximum number of iterations to avoid runaway loops and cost

tool_choice

  • auto (default): Claude decides. any: must use some tool. tool with a name: must use that tool. none: no tools
  • disable_parallel_tool_use: true forces at most one tool call per turn
  • Forced choices (any, tool) skip the text before the call, and they change the cache for the system and tools

Parallel tool use

  • Claude may return several independent tool_use blocks in one response. Run them concurrently and return all results in one user message

Server tools vs client tools

  • Client tools (yours, plus bash, text editor, memory, computer use) run in your application and you send results. Server tools (web search, web fetch, code execution, tool search) run on Anthropic infrastructure and you just read the result
  • Many tools (dozens) bloat context: use tool search or smaller toolsets so Claude can pick well

Good tool design

  • Few, well-named, non-overlapping tools beat many similar ones. Return only the fields Claude needs, with readable names instead of raw IDs
Model Context Protocol

Model Context Protocol (MCP)

What it is

  • An open protocol that connects AI applications to tools and data. One MCP server can serve many clients (Claude Desktop, Claude Code, your app), one client can use many servers
  • Roles: host (the application), client (one connection inside the host), server (exposes capabilities). Messages are JSON-RPC 2.0

Three server primitives, who controls them

  • Tools: functions the model decides to call (search, create ticket)
  • Resources: read-only data the application chooses to load into context (files, records, URIs)
  • Prompts: reusable templates the user triggers (slash-command style)

Transports

  • stdio: the server is a local subprocess. Simple, good for local tools
  • Streamable HTTP: remote servers over HTTP (with authorization, typically OAuth). Older HTTP+SSE is superseded

Building a server

  • Use the official SDK (Python FastMCP, TypeScript SDK): decorate functions as tools, give types and docstrings (they become the schema and description)
  • Inspect and debug with the MCP Inspector
  • Return clear errors. Log to stderr for stdio servers, because stdout carries the protocol and extra prints corrupt it

With the Claude API

  • The MCP connector lets the Messages API call remote MCP servers directly, without your own client. A tool-using MCP client of your own converts MCP tools to Claude tool definitions and relays results

Safety

  • Treat third-party servers like third-party code: least privilege, review what a tool can do, never put secrets in tool descriptions, keep credentials in environment or a secret store, and require confirmation for destructive tools
Agent loop and design

Agents: the loop and how to design one

Definition

  • An agent lets the model decide the steps: it calls tools in a loop, observes results and continues until it reaches the goal. A workflow follows steps that your code fixes in advance
  • Start with the simplest thing: a single call, then a workflow, and use an agent only when the path cannot be predicted. Agents trade cost and latency for flexibility

The agent loop

  • Call Claude with tools, run requested tools, return results, repeat until end_turn. Add a stop condition: max iterations, budget in tokens or money, timeout
  • Keep a clear goal and success criteria in the system prompt. Give the agent the least tools and the least permission it needs

Human in the loop

  • Require approval before irreversible or high-impact actions (sending email, deleting data, payments, deployments). Show the user exactly what will happen
  • Let the agent ask a clarifying question when the request is ambiguous, instead of guessing

Reliability

  • Make tools idempotent where possible, return errors as tool results with is_error, let the agent retry with a limit, checkpoint state so a crash does not restart everything
  • Log every step (prompt, tool call, result, tokens) for tracing and debugging

Multi-agent

  • An orchestrator splits the work and sub-agents run in separate contexts and return short results. Benefits: clean context, parallelism, specialization. Costs: more tokens, more coordination, harder debugging. Use it for broad, parallelizable tasks, not for every job

Memory scopes

  • In-context (this run), session state (your store), long-term memory (memory tool or database). Scope memory per user and never leak it between users
Workflow patterns

Workflow patterns

Five patterns (from Anthropic's guidance on building agents)

  • Prompt chaining: a fixed sequence, each step uses the previous output, with optional validation gates between steps. Use when the task splits cleanly into steps
  • Routing: classify the input first (a small model like Haiku is perfect) and send it to a specialized prompt, tool set or model. Use for different kinds of input
  • Parallelization: sectioning (independent subtasks run at the same time) or voting (same task several times for confidence). Use for speed or reliability
  • Orchestrator-workers: an LLM decides the subtasks at run time and delegates them to workers, then merges results. Use when subtasks cannot be predicted (code changes across files)
  • Evaluator-optimizer: one call generates, another critiques against criteria, loop until good. Use when you have clear evaluation criteria and iteration helps

Choosing

  • Known fixed steps: chain. Different input types: route. Independent pieces: parallelize. Unknown number of steps: orchestrator-workers. Quality needs iteration with a clear rubric: evaluator-optimizer. Open-ended path: agent
  • Each added call adds cost and latency, so justify it with measured quality gains
  • Put validation (schema check, tests, a guard model) between steps to stop errors from compounding
Security and prompt injection

Security and safety

Two threat models

  • Direct prompt injection or jailbreak: the user is the attacker and types instructions to bypass your rules
  • Indirect prompt injection: the user is trusted but Claude reads third-party content (web pages, emails, documents, tool results) that contains hidden instructions

Defenses against indirect injection

  • Deliver untrusted content only inside tool_result blocks, never in the system prompt or plain user text
  • Say in the tool description or result where the content comes from and that it is untrusted
  • State a policy in the system prompt: content from tools is data, never instructions
  • JSON-encode untrusted strings so they cannot break out of delimiters
  • Do not put your own instructions inside tool results, put them in the user turn after them
  • Least privilege: give the agent only the data and actions it needs, sandbox execution, require human approval for sensitive or irreversible actions
  • Screen tool output with a small model (for example Haiku 5.5) using structured outputs. Treat a refusal of the screening call as a positive verdict
  • Red-team with adversarial documents before launch and monitor in production

Defenses against direct attacks

  • Harmlessness screen on user input with a small model, input validation for known patterns, a system prompt that states boundaries and how to refuse, throttling or banning repeat offenders

Secrets and data

  • API keys live in environment variables or a secret manager, never in code, prompts, tool descriptions, git, client-side apps or logs. Rotate on leak. Use separate keys per environment and workspace spending limits
  • Do not send more personal data than needed. Mask or tokenize PII before the prompt, check retention and zero data retention options, and respect regional requirements when choosing a platform
  • Validate and sanitize model output before using it in a SQL query, shell command, HTML page or file path. The model output is untrusted input to the rest of your system

Safety behavior

  • Claude can refuse. Handle refusal gracefully, give the user a clear message, and do not loop retries
  • Add output moderation and human review where the cost of a wrong answer is high
Claude Code

Claude Code essentials

What it is

  • An agentic coding tool in your terminal and IDE: it reads your code base, edits files, runs commands and uses tools, with your permission

Project memory

  • CLAUDE.md files give durable project context (build and test commands, conventions, architecture notes). Locations: project root (shared with the team in git), user level in ~/.claude/ (personal), and in sub-folders (loaded when relevant)
  • Keep it short and specific. Long vague files waste context

Permissions

  • Tool use needs approval by default. Settings define allow, ask and deny rules (for example allow npm test, deny reading .env). Deny wins over allow
  • Permission modes range from asking for each edit to auto-accepting edits and plan mode (read-only planning before changes)
  • Settings scopes: user, project (shared) and local (not committed). More specific scopes override broader ones

Extending it

  • Slash commands: reusable prompts in markdown files
  • Skills: folders with instructions and scripts that Claude loads when relevant
  • Sub-agents: specialized agents with their own context and tool limits
  • Hooks: your shell commands that run at lifecycle events (before or after a tool call, on prompt submit, on stop). Unlike a prompt, a hook is deterministic: use it to enforce formatting, block dangerous commands, run tests
  • MCP servers: connect issue trackers, databases, browsers
  • Headless mode (claude -p) and the Agent SDK run it from scripts and CI

Good habits

  • Explore and plan first, then implement, then verify with tests. Give Claude a way to check its own work. Clear context between unrelated tasks
Evals and debugging

Evals, testing and debugging

Why evals

  • Prompts and models change. Without an eval set you cannot say whether a change helped. Evals define "done" and catch regressions

Building an eval

  • A set of realistic inputs with expected outcomes (golden answers or criteria), including edge cases and past failures. Start small (dozens), grow it from real production failures
  • Graders: code-based (exact match, schema, tests: fast and cheap), LLM-as-judge (rubric, flexible, validate against human labels), human (slowest, gold standard)
  • Make criteria specific and measurable. Judge one dimension at a time. Use a different or stronger model as the judge when possible
  • Run evals before each prompt, model or tool change, and in CI. Batch API makes big eval runs cheap

Debugging an LLM system

  • Trace the full flow: prompt, tool calls, tool results, stop reason, tokens, latency, cost, request id
  • Classify failures: missing context, ambiguous instruction, bad tool description, tool bug, truncation (max_tokens), wrong model for the job, injection
  • Reproduce with the exact input, change one variable, compare on the eval set
  • Monitor in production: quality samples, error and refusal rates, latency, cost per request, tool failure rate. Alert on drift

Testing around the model

  • Mock the API for unit tests of your own code. Use real calls in a smaller eval and integration suite. Do not expect identical text, assert on structure and properties
